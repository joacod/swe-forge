# SWE Forge v0.1.0-alpha.1

This is the first-alpha release candidate for SWE Forge: an experimental,
opt-in, harness-agnostic coding workflow with a portable canonical core and
asymmetric harness adapters.

## Publication status

The release artifacts and package metadata are prepared locally. This task does
not create a Git tag, GitHub Release, registry publication, or external upload.
Publication remains a separate manual action.

## Highlights

- Standalone executables carry the canonical workflow, adapter projections, and
  portable tools without requiring a repository checkout, Bun, Node.js, or
  Python at runtime.
- Managed standalone releases use immutable
  `versions/<version>/canonical` directories and one global `current` symlink.
- Harness-local manifests and projections share the active canonical release;
  standalone `update` activates once and reconciles every managed harness.
- Installation, verification, status, doctor, update, and uninstall preserve
  conflict refusal, rollback, and shared-support ownership.
- `SOLO` is the default topology, with bounded native `SUBAGENTS` delegation
  where demonstrated capability makes it useful.
- Pi is First-class, OpenCode is Compatible, and OMP, Claude Code, Codex, and
  Cursor are Experimental; no adapter parity is implied.
- The Bun package entrypoint is prepared without postinstall downloads or
  runtime npm dependencies.

## Standalone artifacts

The release builder currently accepts:

| Artifact target | Filename |
| --- | --- |
| macOS arm64 | `swe-forge-v0.1.0-alpha.1-darwin-arm64` |
| Linux x64 (glibc) | `swe-forge-v0.1.0-alpha.1-linux-x64` |

Each artifact is accompanied by `<artifact>.json` and `<artifact>.sha256`.
Metadata records the release version, target, Bun version, source commit/tree
state, artifact SHA-256, embedded payload SHA-256, and asset count. The payload
identity is deterministic for the tracked source inventory and `VERSION`; Bun
may still produce different complete binary bytes on separate builds.

Before manual distribution, run the clean-room validation command against the
artifact and verify its checksum sidecar:

```bash
bun run scripts/test-standalone-release.ts \
  build/releases/v0.1.0-alpha.1/swe-forge-v0.1.0-alpha.1-darwin-arm64
```

## Installation modes

### Standalone executable

```bash
./swe-forge --version
./swe-forge install pi
./swe-forge verify pi
./swe-forge update
```

The executable activates its embedded release globally under the user data
root. `update` never downloads a newer version, contacts a registry, switches
branches, or removes older immutable versions.

### Bun global package

After a separate package publication, the prepared metadata supports:

```bash
bun add --global swe-forge@0.1.0-alpha.1
swe-forge --version
```

This package entrypoint intentionally runs source-checkout mode and requires
Bun. It is distinct from the runtime-closed standalone artifacts. The package
is not published by this task.

### Source-checkout developer mode

Use the [installation guide](../installation.md) for the reviewed checkout
workflow. It requires Bun and keeps updates per harness; it does not activate
managed standalone releases.

## Compatibility and limitations

See the [compatibility record](../compatibility.md) for support tiers,
projection evidence, real-harness validation, and standalone platform gates.
The first alpha remains experimental, adapter compatibility is asymmetric, and
projection success is not behavioral harness validation.

The optional Pi `swe_forge_subagent` package remains a separately reviewed
local integration and is not installed by the standalone executable or the
main package. Native delegation falls back to root-owned sequential work when
the host capability is unavailable.

SWE Forge may create a PR in PR mode but never merges automatically. This
release preparation adds no automatic network update or publication behavior.
