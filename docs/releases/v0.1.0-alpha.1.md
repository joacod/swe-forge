# SWE Forge v0.1.0-alpha.1 (planned)

SWE Forge is an experimental, opt-in, harness-agnostic coding workflow with a
portable canonical core and optional harness adapters. This document describes
the planned first public compatibility record and the installer/evidence safety
boundaries. The tag and release are not yet published; publication is reserved
for a separate release task.

## Highlights

- `SOLO` by default, with bounded `SUBAGENTS` delegation when demonstrated
  native capability materially improves one ticket workflow.
- Final alpha hardening covers exact-content evidence, single-checkout
  conformance, and truthful delivery/release boundaries.
- `GUIDED` and opt-in `PR` delivery modes.
- First-class Pi, Compatible OpenCode, and Experimental OMP, Claude Code,
  Codex, and Cursor adapters.
- Registry-driven projections for Pi, OpenCode, OMP, Claude Code, Codex, and Cursor
  without a feature-parity requirement.
- Transactional installation, verification, lifecycle inspection, and safe
  update/uninstall behavior.
- Executable validation and delivery evidence with optional routing
  metadata.

## After publication: upgrade or install

The tag is reserved for the planned first alpha but is not currently
published. There is no released installation source yet. After the separate
release task publishes the tag and release, use a tagged source checkout
rather than mutable `main`:

```bash
# Use only after the v0.1.0-alpha.1 tag and release are published:
git clone --branch v0.1.0-alpha.1 --depth 1 \
  https://github.com/joacod/swe-forge.git ~/tools/swe-forge
cd ~/tools/swe-forge
scripts/swe-forge install pi
scripts/swe-forge verify pi
```

Until publication, `main` is development-only and must not be advertised as a
released installation source.

For an existing managed development installation, run `version`, `status`,
`doctor`, and then `update <harness>` after reviewing the current checkout. Do
not treat that development installation as the future published release.
Legacy installations without a managed manifest must be recreated before
destructive lifecycle operations are available.

## Compatibility

See [the compatibility record](../compatibility.md), which separates support
tier, projection/fixture validation, and real harness validation. Pi has the
strongest current validation evidence and OpenCode has prior successful use.
OMP has now passed a read-only real-harness smoke test; Claude Code, Codex, and
Cursor have not been behaviorally exercised. The installer and projection
fixtures for those remaining adapters do not establish behavioral validation.

## Known limitations

- Alpha behavior and asymmetric adapter compatibility may change; projection
  success does not establish real harness support or feature parity.
- Installations are user-level source links; Pi's optional runtime extension
  depends on the observed Pi lifecycle API and remains capability-negotiated.
- Native delegation is optional and asymmetric across harnesses; unavailable
  capability falls back to root-owned sequential work.
- SWE Forge creates a PR in PR mode but never merges it or publishes releases
  automatically.

Please use the [real-run report template](https://github.com/joacod/swe-forge/issues/new?template=real-run-report.md)
to report friction, unnecessary ceremony, and useful evidence.
